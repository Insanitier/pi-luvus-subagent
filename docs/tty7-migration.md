> 目的：在写第一行迁移代码之前，把**我们现有每一处实现**与 **tty7 已有的能力**逐条对齐，明确
> "直接用它的 / 我们保留的 / 需要新设计的 / 明确没有的"，避免重造轮子。
>
> 本文是**留档**：上下文被压缩后应从这里恢复，不要重新调研。
>
> 判定用词：
> - **采用**：tty7 已有等价能力，我们不再自己写。
> - **改用**：tty7 的能力比我们的更好，按它的换掉我们。
> - **保留**：与终端底座无关的协议逻辑，代码不动。
> - **新增**：tty7 没有、必须我们自己设计。
> - **丢弃**：换底座后这段代码应删除。
>
> 取证：两个 explorer 并行取样（代码面清点 / tty7 全量文档 38 页 + 仓库 skill 三文件）+
> 本机实测（见 §1）。凡标 **推断** 的，是没有原文/实测支撑的判断，必须由 §7 的探针结论替换。

### 1.2 两台 server 的实测对账（回答"能不能用 Windows 侧 CLI"）

| | Windows 侧 | WSL 侧 |
| --- | --- | --- |
| server | `tty7-app.exe` 自带 daemon：pid 20020、**panes: 0**、`control_version 12`、`protocol_version 6`、`build 26.10.1-nightly.202610202101`、TCP `control.port` 52253 | `tty7-server-c12p6 --daemon`：unix `control.sock`，`machine.json` 记着 **pane 3**（~/projects/Soil_pe）与 **pane 4**（~/projects/misc = 本会话）；pane 环境自报 `TTY7=26.9.4` |

| CLI 能看到什么 | `machine ls --json` → `{"machines":[]}`；`status --json` → `panes: 0` ⇒ **看不到也连不到 WSL 的 pane** | — |
| 通道 | app 通过 `tty7-server --stdio[--serve\|--bridge]` 桥到 WSL（app 独占的通道，不是可路由的 machine；unix socket 也不是 Windows 进程能拨的） | daemon 的 `control.sock` 就是给 CLI 用的 |

**CLI 自己的帮助原文**（`tty7.exe --help`）：

> "One name, three artifacts: this CLI, the tty7 GUI (tty7-app), and tty7-server."
> "The GUI and this CLI are both clients of the server on each machine — neither needs the other to be running."
> "**An agent reaches the server through this binary, not through a wire protocol of its own.** Inside a tty7 shell, `$TTY7_CONFIG_DIR` points at the server, and `$TTY7_PANE` / `$TTY7_WS` let the address-taking verbs run with no address given."

⇒ 官方设计就是"每台机器一个 server，agent 用同机 CLI 连它"。我们的 agent 在 WSL ⇒ WSL 侧必须有一个 `tty7` CLI 二进制。**这不是再装一个终端**：daemon 已由 app 起好、窗口照旧显示，缺的只是客户端那半个。

**版本差（实测）**：WSL server **26.9.4** vs Windows app **26.10.1-nightly**；installer 的
`server/tty7-server-linux-x86_64-musl` 也是 26.10.1，且**只带 server，不带 CLI**
（实测 `agents --json` 仍被拒）。所以 Linux CLI 需另取；并且给 26.9.4 的 daemon 配客户端要留意
`control_version`/`protocol_version` 拒绝。**升级 WSL daemon 会杀掉它所有的 pane（含本会话）**，
只能在用户选定的时刻做。

### 1.3 P0 结案 + P1 首测（均为实测，2026-10-21）

**取到 Linux CLI**（GitHub nightly 发行包，只解出 CLI 一个文件，43 MB tar.gz → 8.5 MB 二进制）：

```
https://github.com/l0ng-ai/tty7/releases/download/nightly/tty7-26.10.1-nightly.202610202101-linux-x86_64.tar.gz
→ tty7-…-linux-x86_64/tty7     # 8.5 MB，`tty7 26.10.1-nightly.202610202101`
```

**方言对账（这才是版本门槛，不是版本号）**：

| | control | protocol | build |
| --- | --- | --- | --- |
| WSL 在跑的 server（旧） | 12 | 6 | **26.9.4** |
| Linux CLI（新） | 12 | 6 | 26.10.1-nightly |

⇒ **12/6 == 12/6**，新旧 CLI/server 可以对话。用户的判断正确：服务端旧一点本身不是问题。

**实测三条（`TTY7_CONFIG_DIR=/home/ft183/.config/tty7`）**：

```
$ tty7 status --json
{"pid":467,"panes":2,"control_version":12,"protocol_version":6,"build":"26.9.4","socket":"/home/ft183/.config/tty7/control.sock"}

$ tty7 agents --json
{"agents":[{"pane_id":4,"agent":"Pi","state":{"status":"working","session_id":"01a142d7-…","launch_argv":["pi"],"rich":true,"turns":1,"inferred":false,…}}]}

$ tty7 pane ls --json
{"panes":[{"pane":4,…,"cwd":"/home/ft183/projects/misc"},{"pane":5,…}]}
```

**结论**：
1. **P0 关闭**：WSL 侧 CLI 可用，**连到的是同一个 daemon**（`build: 26.9.4` + 我们自己的 `control.sock`），不是新 server。**不需要重启 daemon、不需要动任何 pane。**
2. **P1 第一问已答**：tty7 把本会话认成 `agent: "Pi"`，`inferred: false`（**声明式**，不是猜的），带 `session_id` 与 `turns`。
3. **§8.2 的修正**：我说的"luvus 起的子代理没有 TTY7"需要更精确——**只要子进程的 pane 是 tty7 的 pane，它就会继承 `TTY7`/`TTY7_PANE`**（本会话正是 luvus 起的，`launch_argv: ["pi"]`，仍然被正确识别）。真正决定的是**pane 从哪来**，不是谁 spawn。luvus 自己的 pane 不是 tty7 pane ⇒ 那里的子代理不报状态。
4. 仍待测（P1 第二问）：**我们自己用完整 argv 起的子 pi**（`--session-dir … --extension … --subagent-child … --system-prompt <file>`）是否同样被认成 `Pi` 且状态随轮次变化 —— 需要在 tty7 里开一个 pane 试。

### 1.4 P1 第二问实测（我们自己的完整 argv 起的子 pi）—— 2026-10-21，环境已切 tty7 原生

前提：本会话已是 **tty7 原生 pane 4**（`TTY7_CONFIG_DIR`/`TTY7`/`TTY7_PANE` 全在），**Luvus 进程已不存在**（只剩二进制）⇒ 现有 `delegate` 通道实际离线。

探针（全程只读 + 我们自己创建的 pane，结束已 `pane close`）：

```
tty7 split --v                      → %6
tty7 send %6 'pi --session-dir ~/.pi/agent/subagent-sessions --session-id probe-tty7-1   --name probe-tty7-1 --extension …/luvus-subagent.ts --subagent-child --no-skills' --enter
```

| 测量 | 结果 |
| --- | --- |
| 是否被识别 | `{"pane_id":6,"agent":"Pi","state":{…,"session_id":"probe-tty7-1","rich":true,"turns":0,"inferred":false}}` ⇒ **认成 Pi，声明式**，`session_id` **正是我们 `--session-id` 钉的值**（可直接与我们的 registry/会话文件对齐） |
| 状态机 | `idle` → 派活后 `working` → `done`，`turns` 随轮次递增（0 → 1 → … → 3） |
| 我们的结果提取 | 子会话文件 `2026-10-21T09-34-07-613Z_probe-tty7-1.jsonl` 有 17 条记录，最后一条 `assistant stop=stop text="PROBE_OK"` ⇒ **`readChildResult` 原样可用** |
| 顺带看到的 | 中间有两条 `assistant stop=error`（pi-retry 重试）⇒ 我们那个"终态要持续成立才认账"的窗口仍然必要 |

**两条新发现（影响设计，必须记住）**：

1. **`wait --until done --changed` 有竞态**：如果子代理的那一轮在 `wait` 开始*之前*就结束了，`--changed` 会拒绝当前这个
   `done`，于是一直等到超时（实测阻塞 72s 被手动终止，而 `turns` 已经涨过）。
   ⇒ 我们的 watcher **不能只靠 `--changed`**：必须在 send 前记下 `turns`，等到 "`turns` 增大 **且** `status=done`"，或 `wait` 返回后用 `turns`/`stale` 复核。
2. **`since_ms` 在本机这个 server（26.9.4）里不存在**（JSON 里没有该字段，文档是给新版本的）
   ⇒ §8.3 的"窗口输入改用 `since_ms`"在本机不成立，必须用 **`turns` + 子会话文件 mtime** 作为"状态是否还在延续"的证据。

#### 关于 `since_ms` 缺失——是哪一层缺（实测对账，2026-10-21）

这台机器上同时存在**两个 server 二进制**，别混：

| 文件 | 版本 | `strings \| grep -c since_ms` | mtime |
| --- | --- | --- | --- |
| `D:\Software\tty7\server\tty7-server-linux-x86_64-musl`（app 自带/会部署的） | **26.10.1-nightly.202610202101** | **2** | 10-21 |
| `~/.local/share/tty7/bin/tty7-server-c12p6`（**正在跑**的 daemon） | **26.9.4** | **0** | **10-01** |
| `D:\Software\tty7\tty7.exe`（Windows CLI） | 26.10.1-nightly | 3 | — |
| `D:\Software\tty7\tty7-app.exe`（GUI） | 26.10.1-nightly | 4 | — |

结论：**字段没被删，文档也没过期**——上游 main 仍在 `AgentState` 里定义它（`Option<u64>`，注释"`None` from a daemon that predates it"），
最新那个 server 二进制里也有它；缺的原因是**正在跑的 daemon 是 10-01 那次安装留下的旧进程**，它自己不会升级。
文档连这个降级都写明了（`tty7 agents` 的 `FOR` 列显示 `-`，实测就是 `-`）。
要拿到它必须让 daemon 换新二进制重启——会杀掉全机所有 pane，只能由用户决定；我们的设计不依赖它。

另外：`capture --plain --tail 18` 对 pi 的 TUI 只取到边框和状态行 ⇒ 印证 tty7 自己的建议——**结果走会话/文件，屏幕只作诊断**。

**措辞修正**：不是"没有通道"，而是 **"pi→tty7 的状态上报通道有；pi→tty7 的控制通道缺客户端"**。两者不能互相替代：`agent-hook` 只能喂状态，不能开 pane / 发键 / 读屏 / 等状态。

**为什么要紧**：现有扩展的一切都通过 CLI 驱动底座（`luvus.ts` 全部 266 行）。tty7 在文档里提供的驱动面同样是 **CLI**（`send/wait/capture/agents/procs/pane`），没有 socket 协议、没有 SDK、没有"上报状态"的 API（§6）。**CLI 不可达 ⇒ 迁移无从谈起。** 必须先解决 P0（§7）。

候选解法（待验证，不要拍板）：
1. 从源码构建 Linux 侧 CLI（仓库公开，文档有 Building from source 一节）；
2. GUI 安装包可能自带 CLI，只是没放进 WSL 的 PATH（需在 Windows 侧确认安装布局）；
3. 用 `tty7-server --stdio --serve` / `--control-sock` 直接对话（**无文档**，属协议逆向，风险高，不建议）——仅在 1、2 都失败时考虑。

## 4. 逐条对照（编号沿用代码面清点，行号见各条）

### 4.1 进程/pane 生命周期

| # | 我们的实现 | 判定 | 依据 / 替换方式 |
| --- | --- | --- | --- |
| 1.1 | `agent start … -- <pi argv>`（`luvus.ts:121`） | **新增** | tty7 无"非阻塞 argv spawn"。两条候选：`split`+`send`（pane id 确定，但过 shell）；detach `run --keep`（argv 直传，但 pane id 靠 `agents --json` 反查，退出码无人收） |
| 1.2 | 粘贴后按 transcript 判 taken/queued/unsent（`handover.ts:51`） | 保留 + 采用 | 保留我们的 transcript 判据（tty7 无 composer 语义）；**并采用**官方 "Prove it started"：首次 `send` 后必须 `capture --plain \| tail -3`，仍停在提示符就补 `send --enter` |

| 1.4 | 关窗 15s 超时、抛错吞掉（`luvus.ts:214`） | 采用 | 保留超时与吞错策略 |

## 7. tty7 与我们冲突/必须遵守的纪律

- **不许 `send` 进不是自己开的 pane**、**不许关不是自己建的 pane/tab/workspace**、**不许 `server stop/restart`**、**不许 `pane close --orphans`**（SKILL.md 明写"人的扫帚，你别挥"）⇒ 我们的 sweeps 只能碰自己的 session 文件（现状正好如此 ✓）；`--orphans` **永远不调**。
- **必须用交互模式，不许 `-p`**（print 模式无 TUI、会话即弃）⇒ 我们的 launch argv 已经是交互 pi ✓。
- **首次 `send` 后必须"prove it started"**（`capture --plain | tail -3`，仍在提示符就补 `--enter`）⇒ 这是 §8.1 的强制步骤。
- **结果收集优先走 git，屏幕只作诊断**（delegation.md）⇒ 见 §9 待定决策 D3。
- **`waiting` 应尽量由我们自己值守**（在任务边界内直接答，越界才上报人）⇒ 见 §9 待定决策 D2。
- 文档自身不一致：网站 CLI 参考 vs 仓库 skill（`exec` 只在 skill；`send`/`capture` 的 JSON 字段不同；"Settings → Integrations" vs "Settings → Agents"）⇒ **以已安装二进制为准**，P0 解决后把 `--help`/`--json` 实样抓进 §1。

## 8. 需要新设计的三处

### 8.1 启动握手（替代 `agent start`）

目标性质（现在有、不能丢）：**父代理开始等之前，就知道"子进程起来了"**；argv 不被 shell 曲解。

方案 A（推荐）：`split --v`（默认目标 `$TTY7_PANE`，子 pane 就在父旁边）→ `send %NEW '<引号化的 pi 命令>' --enter` → **prove it started**（`capture --plain --tail 3`；仍在提示符 ⇒ 补 `--enter`）→ `agents --json` 里该 pane 出现 `pi` 且带 `session_id` ⇒ 启动成功。
需新增：argv→shell 行的引号化（含空参数 `''`）、失败态上报（"命令没跑起来 + 屏幕尾行"）、超时。

方案 B：detach `tty7 run --keep --ws <WS> -- <pi argv…>`（argv 直传）→ 用 `agents --json` 的 `session_id` 反查 pane id。
优点：无引号问题；缺点：pane id 非原子获得、退出码无人收、必须以 `--ws` 指定 workspace（会动用户的 layout 组织）。

**推断**：B 的 `--keep` 语义（"leaves the pane alive as a new tab afterwards"）意味着 pane 只在命令结束后才"留存"，与我们的生命周期不吻合 ⇒ 倾向 A。**待 P3 实测。**

### 8.2 状态映射（hooks → 我们的 outcome）

我们只需要三个终态判据：`done`（本轮结束）/ `waiting`（等输入）/ `exit`（pane 没了）+ `no-agent`（钩子没生效的护栏）。
需确认：pi hook 是否报告 turn 边界（`done`）、是否报告 `waiting`（权限提示/提问）、`session_id` 是否与 `--session-id` 我们钉的 id 一致（用于把 row 与 session 文件对齐）。

**已由代码确认（`~/.pi/agent/extensions/tty7/index.ts`）**：桥的事件词汇已经覆盖我们的需要 ——
`session-start`、`prompt-submit`、`stop`（=turn boundary）、`permission-request`/`question-asked`
（=waiting 的两类）、以及 `auto_retry_start`（Oh My Pi 的重试）。

**但要命的一条**：桥的第一行守卫是 `if (!process.env["TTY7"]) return;` ⇒ **子进程必须继承
`TTY7` 与 `TTY7_PANE`**。tty7 自己建的 pane 天然有这两个变量；**现在由 luvus 起的子代理没有**
（实测本会话有、luvus 起的子会话不会有）⇒ 迁移后子 pane 必须由 tty7 创建，不能再用别的终端
起子进程。这也是为什么 P1 必须在"我们自己的启动路径"下测，而不是在现有 luvus 路径下测。

### 8.3 静默窗口的新输入

保留窗口，但改成：`agents --json` 的 `status === done && since_ms` 连续 > 窗口；辅以 `childLastWriteAt` 作为"它在写"的证据。这样窗口不再依赖我们自己造的时间基准。

### 9.1 计划里没料到、被检查抓出来的三件事

1. **结束判定的输入必须是转录记录，不能是状态**。实现时先用 `turns` 增量，被"子进程启动那一轮先 done"打脸：`waitForSettle` 在进入时取基线，可那时子进程已经 done ⇒ 永远等不到更大的 turns。最终规则：
   `terminalRecordAt(session) > taskRecordAt(session, task)` —— 任务那条 user 记录**之后**出现终态记录才算这一轮结束。`wait` 只是门铃。
2. **地址只能是 pane**。`submitAndConfirm` 原来把 session 名当 pane 用（Luvus 用名字寻址），tty7 用 pane id ⇒ 粘贴发到了不存在的目标。顺手把 `steer` 的"名字→pane"解析交给 tty7 自己（`agents --json` 的 `session_id`），跨会话也能 steer。
3. **后台 watcher 的游标不能在 `continued` 后前进**。否则"续写的那一版答案"（已经在窗口里写进转录）永远不会被认账，只会一直等到超时；游标停在旧终点，下一轮立刻就能认出更新的那条。

另外两条**产品行为**修正：启动失败（没有 tty7 / 没有可 split 的 pane / 子进程没起来）必须是工具结果而不是异常；"终态但一个字都没有"归为 `no-answer`，而不是 `done` + `(no output)`。
